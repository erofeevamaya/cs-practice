**2. Сравнение версий и поиск изменений**

git log --oneline --stat

Показывает историю коммитов в сокращённом виде. К каждому коммиту добавляется статистика изменений: какие файлы были изменены и сколько строк было добавлено или удалено.



git diff HEAD\~2 HEAD -- lab03/calc.py

Показывает различия между двумя состояниями calc.py: версией два коммита назад и текущей версией.



git show HEAD\~1

Показывает содержимое конкретного коммита, включая информацию о коммите и diff внесённых изменений.



Разница между git diff, git show и git log



git diff предназначен для непосредственного сравнения состояний и показывает изменения между ними.



git show показывает один конкретный объект Git, обычно коммит, вместе с его метаданными и изменениями.

git log предназначен для просмотра истории коммитов. Он позволяет узнать, какие коммиты были сделаны и в каком порядке.

Таким образом, diff отвечает на вопрос «что изменилось между двумя состояниями», show — «что было сделано в конкретном коммите», а log — «какая история изменений проекта».



git log -S"def" --oneline -- lab03/calc.py

Команда ищет коммиты, в которых изменилось количество вхождений строки def в calc.py.

В данной версии калькулятора def не используется, поэтому команда не нашла соответствующих изменений. Это показывает, что git log -S удобно использовать для поиска момента появления или удаления конкретного фрагмента текста.



git blame lab03/calc.py

Показывает для каждой строки файла коммит, в котором она появилась или была изменена, а также автора и другую информацию о коммите.

Для calc.py с помощью blame можно определить, в каком из трёх коммитов появились строки сложения, вычитания и умножения.



**3. Вывод**

В ходе работы были созданы три последовательных состояния проекта и отдельные коммиты для каждого изменения. С помощью git diff можно сравнивать версии, git show позволяет подробно изучать отдельный коммит, git log — историю проекта, git log -S — искать изменения конкретного текста, а git blame — определять происхождение отдельных строк.



**git restore lab03/calc.py** восстанавливает файл из текущего состояния HEAD, то есть из последнего коммита. git restore --source=... позволяет указать конкретный источник, например HEAD\~2, и восстановить файл из более старой версии. Если использовать git restore для файла с незакоммиченными изменениями, эти изменения будут потеряны.





**4. Ошибочный коммит и его отмена**



Я добавила деление без проверки на ноль и закоммитила:

"lab03: add division without zero check".

Ошибка была видна в git log --oneline.



Затем выполнила git revert HEAD. Он создал НОВЫЙ коммит,

который отменяет изменения предыдущего. Ошибочный коммит

остался в истории, но его изменения сняты.



Чем revert отличается от git reset --hard:

\- git reset --hard HEAD\~1 удаляет последний коммит из истории

&#x20; и стирает изменения в рабочей папке. История переписывается.

\- git revert не трогает старую историю, а добавляет новый коммит

&#x20; с обратными изменениями.



Почему revert безопаснее для опубликованной истории:

если коммит уже на GitHub, reset --hard перепишет историю,

и у других людей будут конфликты при git pull.

revert просто добавляет новый коммит, всем безопасно.





**5. Тег рабочей версии**



git tag -a v1.0 -m "Рабочая версия калькулятора" создал аннотированный тег

на текущем коммите. git tag показал список тегов, git show v1.0 — содержимое.



Чем тег отличается от ветки:

\- Ветка — это подвижный указатель. При новом коммите она сдвигается вперёд.

\- Тег — это неподвижная метка на конкретном коммите. Он не двигается.

По тегу через полгода можно найти ровно ту версию, которую выпустили.



Теги не отправляются обычным git push — их пушат отдельно: git push origin v1.0.





**6. Эксперимент в ветке**



Создала ветку: git switch -c experiment.

В ней добавила деление с проверкой на ноль:

&#x20;   if x == "/":

&#x20;       if b == 0:

&#x20;           print("Ошибка: деление на ноль")

&#x20;       else:

&#x20;           print(a / b)



Закоммитила: git commit -m "lab03: add safe division".



Вернулась в main: git switch main. Убедилась, что в main деления нет —

оно осталось только в ветке.



Влила ветку: git merge --no-ff experiment.

Флаг --no-ff заставляет git создать отдельный коммит слияния,

даже если можно было просто перемотать указатель. Так в истории

видно, что была ветка и она влилась.



Удалила ветку: git branch -d experiment.



Вывод: рискованные правки делают в отдельной ветке.

Если бы эксперимент не удался, ветку можно было бы просто удалить

(git branch -D experiment), и main осталась бы нетронутой.
